# Application audit — 19 October 2026

**Resolution update:** The six confirmed issues below have since been fixed and regression-tested. See [the fix and verification report](APP_AUDIT_FIXES_2026-10-19.md). The findings below preserve the original audit evidence.

The main regression suites pass, but the application still has confirmed gaps. This audit did not change application behavior or the installed iPhone app. Tests used isolated local databases and disposable QA accounts; no existing patient records were changed and no Google generation requests were made.

## Confirmed issues

### 1. “Delete local data” reports success without deleting the main records

Priority: high. `apps/mobile/lib/features/settings/presentation/settings_screen.dart:383` deletes only sync operations, app metadata, and settings preferences. It does not delete learning records, bookmarks, prescriptions, medication records, prescription image files, or scheduled reminders. Removing queued sync operations can also discard pending uploads or deletions.

A focused widget test opened Settings → Manage saved data, confirmed Delete local data, and observed “Local data was deleted.” The saved learning streak remained in SQLite. This test used an isolated database, not the phone's data.

Expected: either perform the promised complete local erasure, including files and reminders, or clearly describe and implement a narrower reset. User-requested cloud deletion work must not be silently discarded.

### 2. The notification master switch does not control medication scheduling

Priority: medium. The switch at `settings_screen.dart:224` persists `notificationsEnabled`. The reminder providers and scheduler do not read that preference or cancel pending notifications when it changes. OS permission checks are implemented separately and do not enforce the app's switch.

A focused provider test set the master preference to false and rebuilt a single daily plan using a fake scheduler. Thirty notifications were still scheduled. The test did not create device notifications.

Expected: turning the master switch off cancels pending reminders and prevents scheduling until re-enabled. Recording doses should remain available.

### 3. Account deletion is not connected to the mobile Settings action

Priority: medium. `settings_screen.dart:284` only shows an informational message. It never calls the existing authenticated account deletion endpoint. Backend account deletion and session revocation passed live checks, so this is a missing frontend workflow.

### 4. The current streak can remain active after missed days

Priority: medium. `apps/mobile/lib/features/learning/data/local_learning_repository.dart:346` returns the stored current streak without comparing its last activity date with today. The calculator resets it when a later learning activity is recorded, but the displayed count can remain stale before that happens. The dashboard also lacks a local-day dependency for this count.

A focused repository test recorded activity two calendar days ago. With no activity yesterday or today, the current streak returned 1 instead of 0. This is a functional issue independent of the flame's color.

### 5. Some Settings destinations remain placeholders

Priority: medium. Settings → Manage sessions shows “Coming in a later module,” although Profile → Manage sessions has a real screen. Privacy policy, Terms, and Data sources also show that placeholder message (`settings_screen.dart:298` and `:347`).

Expected: connect Manage sessions to the existing route and supply the appropriate documents/source destination for the other entries.

### 6. The combined verification script stops at a formatting check

Priority: low. Ruff formatting fails at `services/api/app/cli.py:175`. This is a formatting issue, not an observed runtime exception. `scripts/verify-local.sh` exits at that first failure, so its later checks were run individually during this audit.

## Verification results

- Flutter: **196 tests passed**, with two opt-in live tests skipped by the default suite. All 210 Dart files passed the format check; analysis reported no issues.
- Backend: **170 tests passed**. Ruff lint passed; strict mypy passed for 73 source files. One dependency deprecation warning concerns Starlette's test-client use of httpx.
- Additional focused audit checks: **three expected-behavior tests failed**, reproducing issues 1, 2, and 4 above. These temporary reproduction tests are outside the repository's regular suite.
- Real HTTP/PostgreSQL scenarios: **29 of 30 passed**, covering profile changes, consent, ownership isolation, prescription CRUD/conflicts/deletion, medication plans and dose events, cascading medication deletion, learning progress, bookmarks, terminology lookup, and session revocation.
- The remaining live scenario failed only because it hardcodes dataset version `2026.08.3`. The running server correctly reports the newer `mediexplain-learning-expansion` version `2026.10.19.1`; the preceding terminology/source/morphology checks passed. The live test expectation needs updating.
- Separate live authentication check passed registration, Argon2id hash verification in PostgreSQL, correct/incorrect login, refresh, logout, revoked-session rejection, and reuse of a persisted session in a new HTTP client.
- Separate local Mailpit check passed password-reset delivery, single use, password change, and session revocation. No email was sent to a real recipient.
- The opt-in Flutter LAN sync test passed using the running API: authentication, refresh, offline save/delete synchronization, keeping a saved medicine after deleting its source scan, medication deletion while ordinary backup uploads are disabled, logout, and login.
- Fresh database migrations and Alembic's schema-drift check passed. The running PostgreSQL schema also passed Alembic's check at revision `c9ce88999c02`.
- API, PostgreSQL, and Mailpit were healthy. Readiness passed through both localhost and the Mac's Wi-Fi address `192.168.63.106`. The installed signed iPhone Release app was running.
- Live database reference counts: **30 lessons, 60 flashcards, 4 quiz questions, 34 medical terms, and 89 medicine identities**. This audit did not add reference records or change quizzes.
- Runtime configuration selects Gemini first and **Ollama `qwen3:1.7b`** as the assistant fallback. A locally simulated Google 429 response triggered the actual Ollama model through the Docker-to-Mac connection. It returned valid structured output in approximately **3.62 seconds**, with the correct model and quota-fallback attribution. Google was not contacted. The 8B model remains installed but is not selected. The QA-loaded 1.7B model was unloaded afterward to restore memory usage.
- The backend key file remains Git-ignored with private `0600` permissions. Its contents were not printed.
- No temporary QA accounts remained after testing.

## Limits of this audit

Live Gemini image recognition and generated medicine explanations were not repeated because the previously reported daily quota was exhausted. Mocked cloud success/failure and fallback behavior passed the regression tests, but that does not establish current live cloud availability or the accuracy of difficult handwritten prescriptions.

Physical camera capture, Face ID prompts, actual background notification delivery, voice input, and share-sheet behavior were not manually exercised on the iPhone during this audit. The installed build had already passed signing/build/launch checks; no new native build was needed for a read-only audit. Android compilation was not repeated.

`apps/admin` source is absent from this checkout, so the admin web application's UI, build, and browser tests could not be checked. Backend admin tests are included in the passing API suite. The current application is a local development deployment: the Mac and backend must remain available on the same reachable LAN. A hosted production deployment and approval of reference learning content remain separate release requirements.
