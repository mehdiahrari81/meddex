# Thesis use case implementation audit

Reviewed on 21 October 2026 against `/Users/mahdiahrari/Desktop/mehdi thesis.docx` and the current source in `/Users/mahdiahrari/Developer/meddex`.

The thesis defines **10 unique use cases**, UC1–UC10, in sections 2.6 and 2.7.1. Figure 2.1, the requirements traceability matrix, and chapter 4 repeat those same cases; they are not additional cases.

**Nine core patient workflows are implemented. One administrator workflow is partially implemented. No use case is entirely without implementation.** This is 9/10 coverage of the main user flows, not a claim that 90% of every detailed acceptance criterion is satisfied or that every feature has been verified on a physical phone.

“Core flow implemented” means the described main action has connected application logic, storage or service support, and a mobile interface. It does not mean that every test example, screen name, error message, or performance target in the thesis matches the application exactly. Those differences are listed below.

## Detailed differences from the thesis

These prevent a claim that all ten cases and all their documented test scenarios are completely satisfied:

- **UC1:** The current policy requires 12–128 characters with uppercase, lowercase, number, and symbol. The thesis's successful `Password123` example would be rejected. The form has no confirm-password field, and successful registration establishes a session rather than requiring a second login. These are documentation/behavior differences; the stronger password policy should be retained.
- **UC2:** Nonexistent accounts and wrong passwords use a generic credential error. The thesis proposes a distinct “account does not exist” message, which would disclose registered accounts. The current generic behavior is intentional security behavior.
- **UC3/UC10:** The complete structured scan flow targets prescriptions and medicines. The term camera supports selecting words from medical documents, but arbitrary report-wide extraction and explanation has not been established by this audit. Unclear handwriting, provider outages, and unmatched references remain practical limits.
- **UC5:** Timestamps are stored but not displayed in the recent-search rows. Tapping a history entry returns search results before the explanation. Empty history and history-load errors hide the recent-search section instead of showing the dedicated messages in the thesis. The cached history provider is invalidated for deletion/clearing but not after recording a search, so an already-loaded list can remain stale.
- **UC6:** The list is alphabetical, but there is no select-letter-A interaction. Blank search displays the initial search screen rather than the thesis's proposed empty-input error. The browse query defaults to 50 items without a pagination control in this screen, which would matter as the catalog grows.
- **Architecture:** Earlier chapters and the conclusion still describe Flask and SQLite/MySQL on the server, while the implementation uses FastAPI/PostgreSQL and Drift/SQLite on the phone. Chapter 5 already describes much of the actual stack. The scan description also needs updating for the current cloud AI workflow and confirmation-before-explanation flow.
- **Performance and testing claims:** The 5–10 second processing target is not guaranteed for all scans. Chapter 6's statement that all ten use cases are implemented and pass every scenario is too strong given the absent admin UI and the differences above.

- Tests used isolated databases and mocked external services. This run did not upload patient images, call live AI providers, or repeat physical iPhone camera/background-notification testing. Search-history presentation differences and absent admin frontend are code findings; the selected tests do not cover every thesis acceptance scenario.
