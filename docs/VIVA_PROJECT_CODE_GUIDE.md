## 1 Your opening explanation

> MediExplain is a medical literacy application. A patient can photograph a prescription, review the recognized medicine details, confirm the list, and request simple explanations. It also provides medical terminology search, word breakdowns, lessons, flashcards, quizzes, medication schedules, and taken or skipped records. The phone application uses Flutter. A Python FastAPI service handles authentication, online medicine references, AI requests, and supported synchronization. PostgreSQL stores server data, and Drift manages a separate SQLite database on the phone. AI helps read and simplify information; trusted reference records supply the medical evidence.

Be ready to explain these five distinctions:

| Terms | Difference in this project |
| --- | --- |
| Flutter and Dart | Flutter is the UI framework; Dart is the programming language used to write the mobile application. |
| FastAPI and Python | FastAPI provides HTTP routing, validation integration, and dependency injection; Python is the backend language. This checkout does not use Flask. |
| PostgreSQL and SQLite | PostgreSQL is the shared server database. SQLite is the local phone database. They serve different jobs. |
| OCR and explanation | OCR recognizes writing. Structuring separates medicine fields. Explanation uses a resolved medicine identity and supporting reference facts. |
| Cloud AI and local AI | Gemini and Groq are called over the internet by the backend. Ollama serves the small Qwen3 1.7B model on the laptop for supported text fallback. |

## 4 How to read the code

### The feature folder pattern

For example, `features/prescription/` contains:

- `presentation/`: what users see and tap, including camera, preview, review, correction, and explanations screens.
- `application/`: workflow coordination and algorithms. It decides what should happen next.
- `domain/`: medicine/prescription types, states, and contracts. It describes the feature's vocabulary.
- `data/`: actual local storage, network calls, image storage, and device/provider implementations.

Not every feature has all four folders. Some screens and repositories are large files containing several related classes.

### Recognize these code constructs

| Code construct | Plain explanation | Example in this project |
| --- | --- | --- |
| `class` | A named type containing data or behavior | `AuthController`, `ScheduleEngine`, `MedicalTerm`. |
| `enum` | A restricted set of named choices | `AuthStatus`, prescription pipeline states, dose actions. |
| `abstract interface class` | A contract an implementation must satisfy | `AuthRepository`, `SyncTransport`, medical provider interfaces. |
| `extends` / `implements` | Inherits behavior / promises to satisfy a contract | `ApiAuthRepository implements AuthRepository`. |
| `Future<T>` and `async` / `await` | A result that becomes available later | Waiting for login, a database write, or AI response. `await` does not make remote work instantaneous. |
| `Stream<T>` | A sequence of updates over time | Watching saved medications or records so the UI refreshes after changes. |
| `ref.watch(...)` | Subscribe to a Riverpod dependency | Rebuild a screen when settings or data changes. |
| `ref.read(...)` | Obtain a dependency to perform an action | Call the workflow controller after a button tap. |
| `ref.invalidate(...)` | Discard cached provider state and recompute | Retry loading explanations or refresh content. |
| `ConsumerWidget` | Flutter widget that can access Riverpod | A screen that watches a provider. |
| `StatefulWidget` / `setState` | Widget with local changing UI state | Camera initialization or a loading flag. |
| `@router.post(...)` | Expose a Python function as an HTTP endpoint | Registration or medicine batch explanation. |
| `Depends(...)` | Ask FastAPI to supply a dependency | Current identity, database session, settings. |
| `db.add(...)`, `db.commit()` | Stage a database change, then commit the transaction | Creating an account or content revision. |
| `select(...).where(...)` | Read rows matching conditions | Find only a prescription owned by the current user. |
| `model_validate(...)` | Validate/parse a Pydantic object | Turn incoming or returned data into a checked schema. |
| `try` / `except` or `catch` / `finally` | Handle failure and guaranteed cleanup | Report a network error and always clear a busy flag. |
| Leading `_` in Dart | Library-private implementation detail | `_performRefresh`, private widget-state classes. |
| `const`, `final`, `?`, `!` in Dart | Constant, assigned-once variable, nullable type, explicit non-null assertion | Do not describe `!` as validation; it assumes the programmer's null check is correct. |

### Dependency injection in one example

A screen receives its prescription controller through Riverpod. The controller obtains a repository and OCR/structuring providers. Production wiring gives it real storage and network adapters. A test overrides the same providers with controlled implementations. The screen can be tested without a real phone camera or paid AI request.

### Reading a real method line by line

This is the current `AuthController.signIn` method:

```dart
Future<void> signIn(String email, String password) async {
  state = const AsyncLoading();
  state = await AsyncValue.guard(
    () async => AuthState.authenticated(
      await _repository.signIn(email: email.trim(), password: password),
    ),
  );
}
```

| Part | What to say |
| --- | --- |
| `Future<void>` | The operation finishes later and does not return a separate value to its caller; its result is exposed through controller state. |
| `String email, String password` | Inputs supplied by the form. |
| `async` | Allows the method to await asynchronous work. |
| `state = const AsyncLoading()` | Tells observing widgets that login is in progress. |
| `AsyncValue.guard(...)` | Converts the awaited result into data state or captures a thrown error as error state. |
| `email.trim()` | Removes accidental whitespace around the email; it does not trim the password. |
| `_repository.signIn(...)` | Delegates the actual HTTP/storage behavior to the repository. The controller does not query PostgreSQL itself. |
| `AuthState.authenticated(...)` | Wraps the returned session as the app's authenticated state. |

Now compare this server-side part of `AuthService.login`:

```python
user = self.users.by_email(email.strip().lower())
candidate_hash = user.password_hash if user is not None else _DUMMY_PASSWORD_HASH
password_matches = verify_password(password, candidate_hash)
if user is None or not password_matches or not user.is_active:
    raise InvalidCredentialsError
return self._issue_session(user)
```

The server normalizes the email, retrieves a row, verifies a hash, rejects missing/inactive/wrong-password accounts, and issues a session only on success. A dummy hash allows the password-verification work to run even when no user exists, reducing an obvious timing difference. The mobile controller and backend service cooperate, but they run on different machines and communicate through HTTP.

### Reading a database relationship

In the local `MedicationPlans` table, this declaration links a plan to its medicine:

```dart
TextColumn get medicationId =>
    text().references(UserMedications, #id, onDelete: KeyAction.cascade)();
```

`TextColumn` means a text-valued SQL column. `references(UserMedications, #id)` declares its foreign key. `KeyAction.cascade` makes the database delete dependent plan rows when the referenced medicine is deleted. The complete delete workflow still has to cancel notifications and handle files/outbox state; a foreign key cannot perform those platform actions.

### Reading an API endpoint

In a FastAPI router, a decorator such as `@router.post("/register", ...)` maps an HTTP method/path to a Python function. Its Pydantic payload parameter is validated, and dependency parameters supply database/settings/email services. The function delegates to `AuthService.register`, which performs the actual account/session work. `api/v1/router.py` and `factory.py` add the feature and version prefixes, so the final registration path is `/api/v1/auth/register`.

## 5 The main workflows

### A Application startup

Open [main.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/main.dart), [app.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/app/app.dart), and [bootstrap_provider.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/app/bootstrap/bootstrap_provider.dart).

1. `main()` initializes Flutter bindings, creates an application logger, and starts `MediExplainApp` inside `ProviderScope` and guarded error handling.
2. `bootstrapProvider` wires a deterministic startup sequence through `StartupCoordinator`.
3. Startup prepares environment/configuration, secure storage, authentication, local data, cleanup, settings, connectivity, localization, synchronization wiring, and routing.
4. The app shows a loading or retry screen while startup is incomplete. On success, `MaterialApp.router` uses GoRouter.
5. The root applies language, theme, text scaling, reduced motion, and optional biometric lock. It listens for account/connectivity changes to trigger appropriate refresh/sync work.

**Say aloud:** “The entry point starts Flutter. Startup dependencies must become ready before normal navigation. Riverpod supplies those dependencies, and the root widget applies global settings.”

### B Registration login persistence and logout

```text
AuthScreen → AuthController → ApiAuthRepository → ApiClient
  → POST /api/v1/auth/register or /auth/login
  → Pydantic validation → AuthService → user/session tables
  → tokens → SessionManager → secure SessionVault → authenticated UI
```

Open [auth_screen.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/auth/presentation/auth_screen.dart), [auth_controller.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/auth/application/auth_controller.dart), [auth.py](/Users/mahdiahrari/Developer/meddex/services/api/app/services/auth.py), and [security.py](/Users/mahdiahrari/Developer/meddex/services/api/app/core/security.py).

The form validates inputs. `AuthController.signIn` changes its state to loading, awaits the repository, then exposes authenticated state or an error. `ApiAuthRepository` posts JSON and saves the resulting session. On the server, `AuthService.login` looks up the account, verifies its password hash, and creates an `AuthSession` plus access and refresh credentials.

`SessionManager` restores credentials from secure storage. `ApiClient` adds the bearer access token. A protected request receiving HTTP 401 may refresh the session and retry once. A shared in-flight refresh prevents several simultaneous requests from rotating the same refresh token independently. Logout requests revocation and clears local credentials even if the network is unavailable; offline logout cannot guarantee immediate remote revocation.

**Say aloud:** “Passwords are verified against Argon2id hashes. JWT access tokens are short-lived; refresh tokens are rotated and hashed server-side. A database session lets logout and revocation take effect.”

### C Taking a prescription photograph

```text
Scan screen → camera/import → private image store → preview
  → processing screen → PrescriptionWorkflowController.process
  → image preparation → backend cloud handwriting read
  → full recognized text → prescription structuring
  → validated medicine fields → local prescription draft → review screen
```

Open [prescription_workflow_controller.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/prescription/application/prescription_workflow_controller.dart), [server_handwriting_ocr_provider.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/prescription/data/server_handwriting_ocr_provider.dart), [gemini_handwriting.py](/Users/mahdiahrari/Developer/meddex/services/api/app/services/gemini_handwriting.py), and [prescription_structuring.py](/Users/mahdiahrari/Developer/meddex/services/api/app/services/prescription_structuring.py).

Images can come from a camera, document scanner, photo library, or file picker. They are copied into app-private storage. Image-processing code handles supported orientation, resizing, metadata removal, and quality estimates. Current normal image processing starts cloud reading automatically after the user selects the image; local OCR and the optional CPU handwriting service remain separate capabilities.

The backend reads text and then asks a structuring model to identify medicine-related rows. The output is validated against schema and available source text. The app keeps name, strength, form, dose quantity, frequency, and optional route/duration as distinct fields with review state. Recognized text is not automatically treated as a confirmed medication instruction.

**Say aloud:** “Recognition and structuring are separate steps. The first reads the page; the second organizes only medicine information. The workflow controller saves progress and manages review and error states.”

### D Correcting confirming and explaining the whole list

```text
Review → Check edits fields → Confirm records review for each medicine
  → Explain medicines → separate explanations page
  → one POST /api/v1/prescription-ocr/medicine-overviews for the list
  → resolve identities + collect trusted facts
  → one structured AI batch → validate each result → named explanation cards
```

Open [prescription_review_screen.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/prescription/presentation/prescription_review_screen.dart), [api_medicine_batch_overview.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/prescription/data/api_medicine_batch_overview.dart), and [medicine_batch_overview.py](/Users/mahdiahrari/Developer/meddex/services/api/app/services/medicine_batch_overview.py).

Confirming an item does not immediately request an explanation. Once all retained items are confirmed, the bottom action opens the explanations page. Its provider sends the entire list in one request. The backend prepares reference context for each medicine and generates one batch response. Item IDs tie results to the correct input; missing, duplicated, foreign, or invalid rows cannot silently rename or remove medicines. Reference retrieval may still require multiple medical-source requests; “one AI batch” does not mean the whole pipeline has only one network call.

The server limits a batch to 1–40 unique item IDs and requires `user_confirmed: true`. Output is checked per medicine. If AI generation is unavailable or rejected, supported official source text can still be shown. An unresolved medicine remains a correction case. The workflow separately lets the user add reviewed medicines to My Medications.

**Say aloud:** “User confirmation happens first. Explanations are requested for the complete confirmed list. Medicine identity and sources are validated separately from the model's prose.”

### E Medication plans reminders and Taken or Skip

Open [local_medication_repository.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/medications/data/local_medication_repository.dart), [schedule_engine.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/medications/application/schedule_engine.dart), and [medication_reminder_service.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/medications/application/medication_reminder_service.dart).

1. A user medication stores the medicine itself. A plan stores its reviewed instruction and active/date context. Schedules store times, weekdays, or an interval.
2. Set reminder saves the chosen schedule. `ScheduleEngine.occurrences` calculates actual dose times in the plan's timezone.
3. `MedicationReminderService.rebuild` cancels obsolete pending alerts, omits recorded doses, and schedules the earliest supported occurrences through the notification adapter.
4. Rebuilding uses a rolling 30-day calculation window and defaults to at most 60 pending alerts; it does not schedule an unlimited lifetime of notifications.
5. Taken/Skip writes a dated dose event. The logical dose ID identifies which scheduled dose it belongs to; a revision allows later corrections.
6. Home and history read the saved data. Deleting a medication removes its associated local plans/records and rebuilds reminders; supported remote deletions are queued.

**Say aloud:** “Notifications are scheduled on the device. The server is not contacted every time a dose becomes due. A notification action records an event; it does not just dismiss the alert.”

### F Dictionary search word decoding and learning

Open [resolve_medical_term.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/terminology/application/resolve_medical_term.dart), [word_decoder.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/terminology/application/word_decoder.dart), and [local_learning_repository.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/features/learning/data/local_learning_repository.dart).

Dictionary search uses installed local reference data. It normalizes the input and considers exact matches, aliases, everyday equivalents, abbreviations, partial matches, and spelling suggestions. An ambiguous abbreviation can return several meanings. Term details show definitions, sources, related terms, and stored morphology. Word Decoder first checks known stored components, then tries deterministic prefix/root/suffix matching without forcing unknown fragments into a false result.

Lessons persist section progress. Flashcard reviews update a spaced-repetition schedule. Quiz scoring compares selected option IDs with correct sets. Progress and streaks depend on stored meaningful activity. Today's term is selected deterministically from the local calendar day and refreshes at midnight/resume.

The bundled starter and additive expansion contain 30 lessons, 60 flashcards, 4 quiz questions, and 34 terms in total. These are file-content counts, not a fresh query of every user's database. The assets are marked `production_approved: false`.

### G Offline storage and synchronization

Open [app_database.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/core/database/app_database.dart), [database_provider.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/core/database/database_provider.dart), and [sync_coordinator.dart](/Users/mahdiahrari/Developer/meddex/apps/mobile/lib/core/sync/sync_coordinator.dart).

Local operations update SQLite first. Supported changes enqueue an outbox operation with an entity ID, operation type, payload, and idempotency key. When enabled and connected as an authenticated user, `SyncCoordinator` sends eligible operations through `ApiSyncTransport`. Dependencies prevent a child record being sent before a required parent. Failed requests get delayed retries; successful ones store a server receipt. This is an upload outbox, not proof of a complete bidirectional cross-device merge system.

The database provider switches local databases by account. File names include a SHA-256-derived user identifier; hashing a filename does not encrypt the database. Guest data has its own database. Signing out must not make another user's records appear.

## 6 Important algorithms

| Algorithm | Actual file | How to explain it |
| --- | --- | --- |
| Levenshtein edit distance | `terminology/application/edit_distance.dart` | Counts the minimum insertions, deletions, and substitutions to turn one word into another. The implementation uses two rows of dynamic programming: O(mn) time and O(n) auxiliary space. It supports suggestions, not automatic medicine substitution. |
| Search ranking | `terminology/application/resolve_medical_term.dart` | Gives stronger matches higher scores, sorts candidates, and preserves uncertainty for ambiguous/fuzzy results. |
| Word decomposition | `terminology/application/word_decoder.dart` | Prefers curated morphology; otherwise selects supported long prefix/root/suffix matches and retains unknown fragments. |
| Spaced repetition | `learning/application/spaced_repetition.dart` | SM-2-style scheduling: Again resets repetition, Hard/Good/Easy affect quality and future interval, and ease is bounded. It is deterministic learning logic, not a trained neural model. |
| Quiz scoring | `learning/application/quiz_engine.dart` | For each question, compares the selected answer set with the expected set. Correctness requires matching all and only the correct options. |
| Daily term | `learning/application/daily_term.dart` | Sorts by stable ID, converts the calendar date to a day count, and uses modulo term count. Predictable rotation does not require AI or a daily server job. |
| Reminder generation | `medications/application/schedule_engine.dart` | Filters inactive/as-needed schedules, respects dates/weekdays, converts timezone-aware occurrences to UTC, and handles elapsed-hour intervals separately. |
| Dose conflict resolution | `medications/application/dose_conflict_resolver.dart` | For the same logical dose, higher revision wins; timestamp then ID breaks ties deterministically. |
| Adherence counting | `medications/application/adherence_calculator.dart` | Uses latest dose revisions to count taken, skipped, and unrecorded scheduled doses; separates manual events. It is a record-based summary, not proof of medicine ingestion. |
| Outbox retry | `core/sync/sync_coordinator.dart` | Exponential delay `min(3600, 2^retry)` seconds prevents immediate repeated requests after failure. |
| DRAP normalization | `services/api/app/services/drap_parser.py` | Maps CSV header aliases, validates rows, parses composition, fingerprints records, and removes identical fingerprints. |

**Example to practice:** `tachycardia` can be broken into supported components `tachy`, `cardi`, and `ia`. Explain that this is word formation, not an AI diagnosis.

## 7 Databases and relationships

### Model schema and repository are different

- A **SQLAlchemy model** describes server tables and relationships: `app/models/`.
- A **Pydantic schema** describes allowed API payloads: `app/schemas/`.
- A **repository** performs persistence operations. Mobile `Local...Repository` classes connect domain operations to Drift. Backend user repositories wrap common user/session queries; other server routes/services also query SQLAlchemy directly.
- A **migration** changes existing database structure. Editing a model alone does not upgrade an already-created production database.

### Server table families

| Model file | Main records | Relationship to remember |
| --- | --- | --- |
| `models/user.py` | User, profile, session, consent, password-reset token | One user has their own sessions and personal records. |
| `models/module2.py` | Sources, terms, definitions, aliases, word parts, lessons, flashcards, quizzes, progress, bookmarks | Terms connect to definitions and morphology; progress belongs to users. “Module2” is a historical module label. |
| `models/prescription.py` | Prescription, items, reports, barcode scan | A prescription has several medicine items and an owner. |
| `models/medication.py` | User medication, plan, schedule, reminder time, dose event, note, refill, history, export metadata, privacy | A medicine can have plans/schedules and dated dose records. |
| `models/intelligence.py` | Medicine identity, ingredients, identifiers, provider mappings, facts, resolution, saved medicine, AI conversations, provider health, flags | A catalog identity is reference data; it is different from a patient's personal medication plan. |
| `models/governance.py` | Roles, permissions, memberships, content revisions, reports, imports, audit | Admin permissions govern review/publication/import actions. |

### Local tables

`app_database.dart` combines Drift table groups. `module2_tables.dart` holds terminology/learning storage, `module3_tables.dart` prescription storage, `module4_tables.dart` medicine-intelligence storage, and `module5_tables.dart` medication/reminder storage. Read the actual table class names in the catalogue. The `module4` local grouping does not have to match the numbering in every historical project document.

`app_database.g.dart` is generated Drift code implementing mapping, queries, and companion objects. Maintain table declarations and regenerate it; do not memorize thousands of generated getters for the viva.

### Keys indexes and transactions

Primary keys identify rows. Foreign keys connect dependent records and support referential integrity. Indexes make frequently used lookups cheaper but cost storage and write work. The final server migration creates PostgreSQL's `pg_trgm` extension and a GIN index on normalized medicine names; the existence of that index does not mean every lookup uses fuzzy equivalence. A transaction groups related writes so they commit together or roll back together.

Medicine references retain provider identity, source identifiers/version, retrieval dates, and supporting facts. This provenance lets the app distinguish an official source from OCR text or model-generated wording.

## 8 AI OCR and medical references

Preprocessing, provider routing, structured prompts, validation, batching, caching, and human review are the integration work.

### Why separate providers

Provider interfaces isolate vendor-specific HTTP calls. `CloudProvider` tries configured Gemini and Groq paths for supported quota/availability failures, with bounded time budgets and cooldowns. Text workflows can reach Ollama when appropriate. Invalid credentials and invalid/unsafe output are not automatically treated as quota exhaustion. The small local text model cannot read prescription pixels.

### RAG in this application

RAG means retrieval-augmented generation. Here, medicine resolution and stored/external source facts supply context. `MedicalRagService` selects relevant facts, asks for structured output, checks returned source IDs and other grounding constraints, and returns citations/limitations. It uses relational facts and application selection logic; do not claim that the project necessarily uses a vector database or trains the model on the database.

Grounding checks reduce some errors. They do not prove that every model sentence is medically correct. Patient confirmation records review; it does not clinically verify identity or dosage.

### Reference providers

- **RxNorm:** normalized drug identifiers and terminology; useful for finding an exact medicine concept.
- **MedlinePlus:** patient-oriented medicine information where available.
- **DailyMed:** official drug-label information where available.
- **DRAP dataset adapter:** supports imported Pakistan product records. The local CSV's filename alone is not proof that every entry is a verified regulatory record.
- **PubChem/name resolution and curated brand references:** support exact identity/ingredient resolution with evidence. Regional brands require careful variant matching.

The shipped RxNorm snapshot has 78 records and the curated brand file has six entries in this checkout. They are reference resources, not patient prescriptions. The app may accumulate additional identities in the server database through supported lookups.

### scripts/test_drap_import_db.py

**Purpose:** a manual, database-mutating utility intended to exercise DRAP CSV parsing, governance import, and RxNorm mapping. It is outside the configured backend pytest test directory and is not the app's normal request handler.
